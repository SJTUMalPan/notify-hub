## Context

见 `proposal.md` — Why。设计上有约束作用的事实：

- 当前 `message/` 是空项目，无既有代码、无历史包袱，技术栈可自由选择。
- 投递方是服务器上形态各异的进程（Python 服务、shell 脚本、cron），因此接入层必须是语言无关的 HTTP，且要有一个零依赖的命令行入口给脚本用。
- 通知目标是「我一个人」，不是多租户团队：没有用户体系、没有权限模型、没有并发写入压力，这允许数据层极简化。
- 用户明确要求不做通用投递可靠性（不追求 at-least-once、不做重试队列）。唯一的「必须送达」语义只存在于待办超时提醒这一条路径上，且其实现方式就是「下个周期再提醒一次」。
- 通知渠道首版只做 `webhook` 与 `email`，但用户预期后续要接微信、飞书等 App，所以**适配器接口的抽象质量是本设计的核心**，渠道数量是次要的。

## Goals / Non-Goals

**Goals:**

- 让上游进程以最小成本接入：一次 HTTP POST 或一行 CLI 命令，不需要知道分类规则、渠道配置或待办机制。
- 让「新增一个通知 App」成为纯粹的增量工作：实现一个适配器并注册，不改接入层、分类器与待办逻辑。
- 让「哪些消息要变成待办」由配置决定并可事后追溯判定原因。
- 保证待办在未被处理时一定会被反复提醒，且提醒内容能体现实时超时时长。
- 单进程可跑、单文件数据、无需外部中间件即可部署到一台服务器上。

**Non-Goals:**

- 不做消息队列消费者、不做削峰与背压控制（接入量假设为每秒个位数级别）。
- 不做投递的持久化重试队列与 exactly-once 语义；首次通知失败只记录、不重放。
- 不做多用户、认证授权、审计合规（服务只监听内网/本机，见 Decisions 中的部署边界）。
- 不做消息内容的语义/智能分类，分类完全由规则驱动。
- 不做通知聚合摘要（如「今日 30 条告警合并成一封邮件」）——留待后续变更。

## Decisions

### 决策 1：适配器契约用 `typing.Protocol` + 显式注册表，而非动态插件发现

定义一个渠道无关的统一消息结构（`NotificationMessage`：标题、正文、级别、来源、时间戳、可选超时时长、可选结构化附加信息）与一个适配器协议：

```
class Notifier(Protocol):
    channel_id: str
    def capabilities(self) -> ChannelCapabilities: ...
    def send(self, msg: NotificationMessage) -> DeliveryResult: ...
```

`DeliveryResult` 是显式的成功/失败值对象（`ok`、`receipt`、`error_reason`），而不是靠抛异常表达失败——这直接兑现 spec 中「失败不中断流程」的要求。

**备选方案：**
- *entry-point 动态插件发现（setuptools entry points）*：能支持第三方包安装即生效，但首版所有适配器都在同一个仓库里，这套机制只增加调试难度而不带来收益。留作后续扩展。
- *抽象基类 `ABC`*：与 Protocol 功能等价，但 Protocol 允许适配器不依赖本项目的基类，便于以后把适配器拆成独立包。
- *每个渠道一个独立微服务*：对一个单人通知工具而言部署成本过高，且会让「降级到下一渠道」变成跨进程调用。

### 决策 2：失败语义分两层，只有待办提醒有「重试」

这是本设计最容易被误读的地方，需要在实现时保持清晰：

- **首次通知**（消息刚进来时的投递）：尽力而为。失败即记录 `DeliveryRecord(ok=false, reason=...)`，不重试、不排队。
- **待办超时提醒**：由定时检查驱动。每次检查时，若「距上次通知 ≥ 提醒间隔」，就发一次新的提醒。所谓「重试」不是重发同一条失败请求，而是下个周期自然产生的新提醒。

**理由**：用户明确要求不做可靠性机制，但又要求「长时间没完成就再通知我」。把后者实现为「周期性的新通知」而不是「失败重试」，既满足需求又不引入重试队列与退避状态机。

**备选方案：** 为首次通知加一个内存重试队列 —— 被否决，进程重启即丢，反而制造「以为会重试但实际没有」的错误安全感。

### 决策 3：分类规则用 YAML 配置文件 + 文件监视热加载

规则形态（示意，具体字段在实现时以 tasks 为准）：

```yaml
defaults:
  category: uncategorized
  channel: webhook
rules:
  - id: backup-failure
    match:
      source: [db-backup, file-backup]
      level: [error]
      title_contains: ["失败", "failed"]
    category: backup-failure
    labels: [infra, backup]
    need_ack: true
    channel: email
```

匹配语义按 spec 固定：同一规则内条件之间是「与」，条件内的候选值之间是「或」；关键词匹配区分大小写由配置项显式声明，不依赖实现的偶然行为。规则**按声明顺序首个命中生效**（first-match-wins），这是最容易向使用者解释的语义。

**加载策略**：启动时加载；运行期通过文件 mtime 轮询（间隔数秒）检测变更并重载。解析失败时保留上一份可用规则集并记录告警——绝不因为坏配置而拒绝服务。

**备选方案：**
- *规则存数据库、加管理界面*：可视化的收益对一个单人工具不值当，且规则是「代码化的配置」，放版本控制里更合适。
- *用 Python 装饰器写规则*：表达式能力最强，但改规则要重启、要动代码、无法被非开发者审阅。
- *file watcher 库（watchdog）*：多一个依赖；mtime 轮询在秒级粒度上足够，且行为更容易预测。

### 决策 4：接入层同步受理、异步投递

`POST /api/v1/messages` 的职责边界：校验 → 落库 → 分类 → 生成待办（如需）→ 返回 202 与 `message_id`。**实际的通知投递放到后台任务**（FastAPI `BackgroundTasks` 起步），不阻塞响应。

**理由**：投递要调用外部 App 的 API，耗时在几百毫秒到数秒之间且可能超时；让投递方进程为此等待是不可接受的——那会把通知服务的故障传导成业务进程的卡顿。

**权衡**：202 意味着「已受理」而非「已送达」。这与 spec 的措辞一致（受理结果 + 投递记录可查）。单进程内后台任务在进程崩溃时可能丢一次投递——在「不做可靠性保证」的前提下可接受，且用户可通过投递记录发现。

**备选方案：** 独立的 worker 进程 + 任务表轮询 —— 对单人工具的部署复杂度不划算，留作量级增长后的演进路径（届时接入层契约不变）。

### 决策 5：数据模型（SQLite，SQLModel/SQLAlchemy）

四张表，关系清晰即可，不做过度规范化：

- `messages`：接入原始数据 + 分类结果（命中规则 id、分类名、标签、是否入待办及原因）。
- `todos`：待办状态、首次通知时间、上次通知时间、完成时间、关联 `message_id`；`(source, dedup_key)` 上加唯一约束以保证重复投递不产生重复待办。
- `deliveries`：每次投递尝试（消息或待办、渠道、时间、成功与否、原因、是否首选、是否降级）。
- `todo_events`：待办的状态变更与提醒时间序列（创建、提醒、完成），用于详情页回溯。

SQLite 起步，通过 SQLAlchemy 的方言抽象预留 Postgres。**字段设计上需要注意**：`dedup_key` 为空时不参与唯一约束（否则所有不带该键的消息会互相冲突），唯一性只在 `dedup_key` 非空且待办仍为待完成时成立。

**备选方案：** 纯 JSON 文件存储 —— 「按超时时长排序」「按状态过滤」「投递记录回溯」这几件事一旦要做，就是在手写一个数据库，不如用 SQLite。

### 决策 6：超时提醒用进程内定时任务，间隔固定

一个 asyncio 任务每 N 秒（默认 60）扫描一次待完成待办，对「距上次通知 ≥ 提醒间隔」的逐条发送提醒并更新 `last_notified_at` 与 `todo_events`。默认值：首次提醒门槛 30 分钟、提醒间隔 60 分钟，均可配置。

**理由**：提醒间隔按 spec 是固定间隔（用户已明确选择「同渠道重复提醒」而非递增退避）。扫描式实现天然幂等——它只比较时间戳，不依赖上一次是否成功，因此投递失败后下个周期会自动再试，无需额外的重试状态。

**权衡**：间隔不可小于扫描周期，配置时需校验并给出明确错误。

### 决策 7：完成入口同时提供 Web 页面与 CLI

Web 待办列表用 Jinja2 模板由 FastAPI 直接渲染服务端页面（列表按超时时长降序、每项一个完成按钮），不引入前端框架。CLI 侧 `notify todo done <id>` 走同一个 HTTP 接口。两者共用同一套 service 层方法，避免同一业务逻辑出现两份实现。

**理由**：用户要「手机上也能点完成」，因此必须有页面；同时运维习惯在终端里处理，CLI 是低成本高价值的补充。前端框架（React/Vue）对一个列表页是纯负担。

### 决策 8：部署与安全边界

单进程 uvicorn 常驻，监听地址默认绑定本机回环或内网地址，不作为公网服务暴露。投递方进程与服务同机或同内网。凭据只从环境变量读取，配置文件中出现的是环境变量名；日志与投递记录写入前对 URL 中的 token、密码字段做脱敏。

**理由**：用户的需求是「服务器上的进程通知我」，通信范围天然是内网。这避免了在首版引入认证体系；但**必须在部署文档中显式声明该边界**，防止有人直接把它暴露到公网。

## Risks / Trade-offs

- [后台任务在进程崩溃时丢失一次投递] → 接受：不做可靠性保证是本变更的明确前提；投递记录可查，用户能发现漏投；后续可用 worker + 任务表演进，不影响接入契约。
- [规则匹配是 first-match-wins，顺序敏感，调序可能改变既有分类] → 规则 id 参与 `messages` 记录，可通过「某个分类的规则 id 分布」定位调序带来的影响；部署文档中提示「新增规则优先追加而非前置」。
- [Webhook 平台差异大，`webhook` 适配器的字段映射可能覆盖不全（如飞书要求特定 `msg_type` 结构）] → 字段映射做成可配置而非硬编码；若某平台确需专属逻辑，按适配器契约新增一个专属适配器（如 `feishu`），这正是抽象层要兑现的价值。
- [SMTP 在部分内网环境不可达或被限流] → 邮件作为降级渠道时失败只记录不重试；`/healthz` 不依赖渠道可用性，可区分「服务挂了」与「渠道发不出去」。
- [`(source, dedup_key)` 唯一约束可能误合并「同一批次但语义不同的消息」] → `dedup_key` 是调用方显式声明的字段，不自动生成；未声明即视为需要各自独立，不做隐式去重。
- [单人工具无认证，若被误暴露到公网则可被任意投递甚至触发大量提醒] → 默认绑定回环地址，部署文档把「不要暴露公网」列为强制项；文档同时说明如需跨机器使用应加反向代理与鉴权（后续变更）。
- [规则热加载期间正在处理的消息可能用旧规则分类] → 可接受：规则切换不是事务性需求，记录中保留了命中的规则 id，可解释任何单条消息的分类来源。

## Migration Plan

全新项目，无数据迁移。

**首次部署步骤：**
1. 安装依赖，创建数据目录（SQLite 文件位置可配置）。
2. 写渠道配置：至少配一个 `webhook` 或 `email` 渠道；凭据通过环境变量注入（如 `NOTIFY_WEBHOOK_URL`、`NOTIFY_SMTP_PASSWORD`）。
3. 写分类规则文件，先用最小规则集（默认分类 + 一条针对高优先级来源的规则）。
4. 启动服务，用 `curl` 与 `notify` CLI 各投递一条消息，确认收到通知。
5. 投递一条 `need_ack=true` 的消息，确认待办列表出现该条；把提醒间隔临时调小，确认超时提醒按间隔发出且带超时时长；然后在页面上标记完成，确认不再提醒。

**回滚策略：** 服务可随时停止，投递方进程不受影响（它们只是 HTTP 调用失败）。SQLite 文件保留全部历史消息与待办，回滚不丢数据。若需彻底移除，清理 systemd 单元与数据目录即可。

## Open Questions

- Webhook 载荷的默认字段结构以哪个平台为基准（飞书 / 企业微信 / 通用 JSON）？首版按通用 JSON + 可配置映射实现，等实际接入第一个平台时再把该平台的映射作为示例写入文档。
- 待办是否需要在提醒文案中携带「一键完成」的链接（需要服务可达的地址，涉及内网地址如何在手机上访问的问题）？首版提醒文案只带待办 id 与超时时长，完成动作在页面上做。
