## Why

服务器上多个进程各自需要把消息推给「我」，但目前每条链路都要单独对接一次通知渠道，改一个 App 就要改所有进程。同时纯通知容易在信息流里被淹没——真正需要我动手的事没人跟踪，漏掉就没人再提醒。本变更建立一个统一的消息汇聚与待办跟踪服务：进程只管投递，服务负责分类、投递到我的 App、并盯着需要处理的消息直到我确认完成。

## What Changes

- 新增 **HTTP 接入 API**：进程通过 `POST /api/v1/messages` 投递消息，携带 `source`、`level`、`title`、`body` 以及是否 `need_ack` 等声明字段；单条与批量投递均支持。
- 新增 **CLI 客户端** `notify`：供 shell 脚本、cron、运维命令行以一行命令投递消息（内部走同一个 HTTP 接口，不重复实现业务逻辑）。
- 新增 **消息分类**：以配置文件驱动的规则（按 `source` / `level` / 关键词匹配）完成归类、打标签、决定是否入待办与默认投递渠道。规则可热加载，改规则无需改动投递方代码。
- 新增 **待办跟踪**：声明为 `need_ack` 的消息进入待办，具备 `pending → done` 状态流转；待办超过阈值未完成时，按配置间隔**在同一渠道重复提醒**，提醒文案包含已超时时长。
- 新增 **通知适配层**：定义统一的 `Notifier` 适配器契约（发送、能力声明、错误语义），首版实现 `webhook`（通用 JSON Webhook，覆盖飞书/企业微信/钉钉等群机器人）与 `email`（SMTP）两个适配器；新增 App 只需实现该契约并注册。
- 新增 **Web 待办列表**：一个轻量页面，按超时时长排序展示待办、可直接标记完成、可查看消息详情与投递记录。
- 明确**非目标**：不做消息队列消费者、不做通用投递可靠性保证（不追求 at-least-once）、不做多用户/权限体系、不做消息内容的智能语义分类。

## Capabilities

### New Capabilities

- `message-ingest`: 消息的对外接入契约——HTTP 投递 API 的字段与语义、批量投递、CLI 投递入口、接入侧的校验与错误返回。
- `message-classification`: 配置驱动的分类规则——匹配条件、产出的分类/标签、是否入待办的判定，以及规则变更后的加载行为。
- `todo-tracking`: 待办的生命周期——生成条件、状态流转、超时判定、重复提醒的节奏与文案、完成入口（Web 与 CLI）。
- `notification-delivery`: 通知投递的抽象与实现——适配器契约、渠道注册与选择、投递结果记录、失败处理语义。

### Modified Capabilities

无（项目当前没有任何已归档 capability，全部为新增）。

## Impact

- **新增代码**：`message/` 下新建 Python 服务（FastAPI 应用、分类器、待办调度、适配器包、Web 页面）与 CLI 入口；当前目录为空项目，无既有代码受影响。
- **新增依赖**：FastAPI + Uvicorn、Pydantic、SQLAlchemy 或 SQLModel（SQLite 起步，预留 Postgres）、Jinja2 模板、`httpx`、`click`/`typer`，测试用 pytest。
- **对外接口**：新增 HTTP 端点 `/api/v1/messages`（投递）、`/api/v1/todos`（列表与完成）、`/healthz`；新增命令行工具 `notify`。
- **配置**：新增分类规则文件与渠道凭据配置（Webhook URL、SMTP 账号），凭据仅从环境变量读取，不落库、不入日志。
- **运行形态**：单进程常驻服务 + 定时/内联的超时检查循环；数据落 SQLite 单文件，部署时在每台服务器跑一个实例，进程就近投递。
- **后续扩展点**：新增通知 App 只需实现适配器契约；若来源规模变大，接入层可替换为消息队列消费而不改动分类与投递层。
