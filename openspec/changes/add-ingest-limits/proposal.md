# 给接入端点加上请求体与批量条数上限

## Why

安全审计（P1）指出：`POST /api/v1/messages` 与 `POST /api/v1/messages/batch` 对请求体
**没有任何上限**。批量端点的实现是 `items: list[Any] = Body(...)` —— FastAPI 会把整个
JSON 数组解析成 Python 对象后才进入我们的代码，因此：

- 一个几 GB 的请求体足以把进程内存打满（OOM），服务直接不可用；
- 批量数组的条数没有上限，单条合法消息的处理包含分类、入库与投递入队，
  一个超大数组会把工作队列灌满，长时间占用唯一的投递线程。

这不是「被攻破」级别的问题（端点默认需要令牌），但它是**低成本的自我 DoS**：
脚本写错一个循环、或者上游误把「全量历史」当成一批投递，就能把服务打挂。
审计建议按 fail-closed 处理：**默认设上限**，而不是等出事后再说。

## What Changes

- **新增配置** `server.max_body_bytes`（缺省 1 MiB）与 `server.max_batch_items`（缺省 500）。
  两者都必须显式给正整数；不提供「0 = 关闭」的语义（见 `design.md` D2）。
- **新增 413 响应**：超过请求体上限、或批量数组条数超过上限时，返回 HTTP 413，
  且**不写库、不投递**（整批拒绝，不做部分受理）。据此新增能力
  `message-ingest` 的「接入请求体上限」需求。
- **中间件实现请求体上限**：以纯 ASGI 中间件在**读取阶段**计数并中断，覆盖
  `Content-Length` 缺失（分块传输）的情形，而不是只看请求头。
- **文档与示例同步**：`config.example.yaml`、`docs/configuration.md` 补两个键；
  审计留下的「批量/请求体上限」缺口变成文档契约测试的一部分。

明确**不做**：按来源/渠道分别限流、请求频率限流（rate limit）、并发上限、
排空队列时的背压策略。这些是另一类问题，本次只做「单个请求能塞进来多少」这一层。
