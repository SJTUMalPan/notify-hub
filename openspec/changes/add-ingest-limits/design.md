# 设计：接入端点的大小上限

## D1 上限做成配置，而不是硬编码常量

写死常量会让「我确实需要投递 5 万条历史」变成一个必须改代码、重新发版的死结；
配置化之后代价只是一行 YAML。缺省值按「正常使用远够、异常使用立刻被挡住」取：
1 MiB 正文、500 条批量。实测现有用法（单条消息、CLI 投递）离这两个数都很远。

## D2 不提供「0 = 关闭」的语义

保留期用 `0 = 关闭回收` 是因为「不删除数据」是安全的一侧；这里正好相反：
**关闭上限 = 允许打满内存**，是不安全的一侧。所以两个键都必须是正整数，
`0`、负数、非整数一律在加载配置时报错。要放宽就写一个更大的数字，
让「我主动放大了上限」这件事留在配置里可见，而不是靠一个 `0` 隐式达成。

## D3 请求体上限实现在 ASGI 读取层，而不是只看 `Content-Length`

只看请求头有两个洞：分块传输（`Transfer-Encoding: chunked`）根本没有 `Content-Length`；
伪造一个小的 `Content-Length` 也拦不住实际发送的字节。因此中间件包装 `receive`，
**累计实际读到的字节数**，超过上限立即回 413 并停止向内层应用喂数据。
`Content-Length` 作为快速路径先判一次，省掉无谓的读取。

超限发生在 FastAPI 解析请求体**之前**，所以不会产生半解析的状态；`413` 之后不再调用
内层应用，因此**不会写库**。

## D4 批量条数上限在路由里判，整批拒绝

条数只有解析完 JSON 才知道（数组元素数 ≠ 字节数）。判断点放在 `post_batch` 进入循环之前：
`413` + 明确的中文说明（写清上限与本次条数），不返回 207——「部分受理」会让调用方
以为剩下的被丢掉了是正常的，整批拒绝更不容易被误读。

一个刻意的取舍：数组本身的字节也可能先撞上 `max_body_bytes`，那时返回的也是 413，
只是原因文案不同。调用方按状态码处理即可，两种 413 都是「请求太大，减小后重试」。

## D5 中间件顺序：AuthGuard 仍然在最外层

`AuthGuard` 必须继续是**第一个**看到请求的组件（未认证请求不该有机会消耗读取预算，
也不该因为体积就先被 413 泄露「这个端点存在」以外的信息）。Starlette 的
`add_middleware` 是**后加的更靠外**，因此 `BodyLimit` 要在 `AuthGuard` **之前**注册，
最终顺序为 `AuthGuard(BodyLimit(app))`。

## D6 只对请求体设限，不动响应

响应体积由我们自己的数据决定，不受调用方控制，当前也没有大响应路径
（消息详情、待办列表都分页/有界）。给响应加限制属于「还没出问题就先加复杂度」。

## D7 与 `openspec/specs/message-ingest` 的关系

现有规格冻结了 202 / 422 / 207 三种结果形状，且写明「批量请求中单条消息非法
MUST NOT 导致同批次其它合法消息被丢弃」。本次新增的是**请求级**拒绝（413），
发生在按条处理之前，与「单条非法不影响其它条」不冲突：413 时不是「某条非法」，
而是这一批**整体没有进入处理流程**。因此规格里新增一条需求，而不是修改既有条目。
