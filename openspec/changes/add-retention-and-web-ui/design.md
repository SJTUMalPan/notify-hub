# 设计：有界存储与待办网页改版

## Context

见 `proposal.md` 的 Why。塑造方案的实测事实：

| 事实 | 证据 |
|---|---|
| 当前库 40 KB；载荷最大的是 `messages`（8 行 / 1399 字节），`deliveries` 9 行 / 167 字节 | 对 `~/notify-hub-run/data/notify.db` 逐表统计 |
| `deliveries` 9 行**全部**挂 `message_id`，只有 6 行另外挂 `todo_id` | 同上 |
| `db.py` 开启 `PRAGMA foreign_keys=ON` | `db.py:31,58` |
| `todos.message_id` 是 **FK + unique**；`deliveries.message_id` / `deliveries.todo_id` / `todo_events.todo_id` 都是 FK | `models.py:83,107,108,126` |
| 调度器每天只结算一次：`settled` 时提前 `return 0` | `services/scheduler.py:118-121` |
| `Message` 有 `received_at`（我们收到的时刻）与 `occurred_at`（事件发生时刻） | `models.py:46-47` |

两条最关键的事实：**外键是开的**（删父行前必须先处理子行），**`todos.message_id` 是外键**
（待完成待办会把它引用的消息钉住，删不掉）。

## Goals / Non-Goals

**Goals**

- 长期运行后，五张表的总量由「保留期 + 未完成待办数」界定，而不是随时间无限增长
- 待办网页能看出「今天完成了哪些」，且旧记录可以一键物理回收
- 网页在手机上好看、好用，且**零新增依赖**

**Non-Goals**

- 不做用户体系与权限分级（仍是单用户单令牌）
- 不新增数据表、不改任何既有表结构
- 不改 API 契约、CLI、投递行为、分类规则
- 不做「按条数」的保留策略（只按时间）
- 不做跨进程的回收协调（沿用单进程前提）

## Decisions

### D1：保留期以**本地自然日**计算，`cutoff = 今天 - days`

本地时区复用 `reminders.timezone`（`Asia/Shanghai`），与每日汇总的「自然日」**同源**——
系统里只能有一个「今天是哪天」的定义，否则汇总与回收会在跨日边界上打架。

`retention.days`（默认 30）语义是「**至少保留这么多天**」：回收的是本地日期**早于**
`今天 - days` 的记录。`0` 表示关闭回收。

**备选**：按小时计（`retention.hours`）——被否，用户的心智模型是「天」，而且按小时算会让
「昨天完成的」在一天中间的某个时刻突然消失，不好解释。

### D2：**待完成的待办，以及它们引用的消息，永不回收**

这是硬约束，不是可配置项。理由：待完成待办要进每日汇总，删掉等于**丢用户的事**；
而 `todos.message_id` 是外键，消息被它们钉住，物理上也删不掉。所以：

- `todos.status = pending` → 永不删
- 被任何 todo（无论状态）引用的 `messages` 行 → 永不删

**这意味着存储的下界由「未完成待办数」决定，而不是纯时间。** 一个拖了半年的待办会连它的
消息一起永久保留——这是**语义上正确的**，如实写进文档，不做隐瞒。

### D3：回收挂在调度器的**每日结算点**

`services/scheduler.py:_run_once` 的结构天然合适：未到触发时刻早退；当天已 `settled` 早退；
只有真正完成当天结算的那一次会往下走。把回收挂在**当天结算完成之后**，就天然获得
「每天至多一次」的语义，不需要引入任何新的定时状态。

**备选**：新增独立的后台回收线程——被否，多一个线程就多一处启动/停止顺序、多一处异常隔离，
而收益只是「不必等到 21:00」。**备选**：服务启动时也跑一次——被否，那会让「重启服务」变成
一个会删数据的动作，部署时的心智负担不值得。

### D4：删除顺序受外键约束，`deliveries.todo_id` **解绑而不是删除**

`PRAGMA foreign_keys=ON`，所以顺序不可颠倒：

1. 删已完成待办 → 先删它的 `todo_events`，并把引用它的 `deliveries.todo_id` **置为 NULL**
2. 删消息 → 先删 `deliveries` 里 `message_id` 指向它的行，再删该消息
3. 删过期的 `digest_runs`

第 1 步选择**解绑**而不是连行删除，依据是实测：那 9 行投递记录**全部挂在消息名下**，
`todo_id` 只是附加归属。删行会让消息详情页的「投递记录」凭空少掉几行——**页面会说谎**
（「这条消息没投递过」，可它明明投递成功过）。省下的是 6 行、约 100 多字节，换掉审计不划算。

### D5：网页的「清空已完成」= 同一个回收引擎，`cutoff = 今天`

按钮语义是「删掉已不在栏目里显示的旧记录」：删除完成日期**早于今天**的已完成待办
（今天完成的保留），连带它们的 `todo_events`，`deliveries` 同样解绑。

它与自动回收是**同一个引擎、不同的 cutoff**。网页**不直接访问数据库**，只调用服务层——
这是既有分层的要求（`web/routes.py` 的文件头明确写着「只读经 `ctx.todos` / `ctx.messages` 取数」）。

### D6：「最近完成」栏目只显示**今天**完成的（本地自然日）

与用户确认过的窗口一致：次日 00:00 自然消失。判定用 `completed_at` 换算到本地时区后的**日期**。

**必须用 `ctx.clock.now()`，不得调用 `datetime.now()`**——后者让测试无法控制时间，
也破坏既有的时钟注入不变量。

### D7：美化只改 `base.html` 的内联 CSS，零外部资源

- 不新增 `<link>`、不新增 `@import`、不引入 webfont、不引入任何 JS 库
- 保持系统字体栈；手机优先（用户主要在手机上用）
- 表格在窄屏不能横向撑破页面
- 「清空已完成」是破坏性操作，表单加内联 `onsubmit="return confirm(...)"` 二次确认
  （内联属性，不引入脚本文件）

**备选**：抽成独立 `.css` 静态文件——被否，那需要挂载 `StaticFiles`，改动面比收益大。

### D8：新增 `RetentionService`，由组合根装配

它持有 `db` / `clock` / `logger` 与 `days`，对外暴露两个方法（完整签名见 `architecture.md` §4.2）。
调度器与网页都通过它回收，**没有第二处删除逻辑**。

## Risks / Trade-offs

- **自动删数据是破坏性能力** → 默认 30 天；`days: 0` 可关；每次回收记录删了多少行；
  文档明确写出「删了就没了，重要数据请自行备份」。
- **待完成待办导致存储仍有下界** → 语义必需（见 D2）；如实写进文档，不假装完全有界。
- **回收发生在 21:00 之后**（结算点）→ 若服务当天一直没跑到触发时刻，回收顺延到次日结算；
  不引入额外触发点来「准时」。文档说明。
- **两个窗口并存**：「最近完成」栏目是 1 天窗口，自动回收是 30 天窗口。文档必须写清它们是
  独立的两件事，否则会让人以为「页面上看不到了就等于被删了」。
- **美化的回归风险**：既有 `tests/test_web.py`（635 行）对页面内容有断言 → 改动后全量必须仍全绿。

## Migration Plan

1. 配置里新增 `retention` 段（可省略，缺省 30 天）
2. 升级并重启服务；首次回收发生在当天结算之后
3. **回滚**：把 `retention.days` 设为 `0` 并重启即可停止回收；已被删除的历史**无法恢复**，
   所以首次上线前建议先备份 `notify.db`
